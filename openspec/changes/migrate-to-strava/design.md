## Context

**The archive** — the term used throughout this change — is the unpacked Endomondo GDPR data export dated 2020-11-01, located at `data/endomondo-strava-exports/endomondo-2020-11-01/` (git-ignored personal data; the directory is configurable, this is its actual location). Migration reads exactly two of its subdirectories:

- `Workouts/` — 324 files forming **162 same-basename pairs** named `YYYY-MM-DD HH_mm_ss.0` + `.json`/`.tcx`. The JSON carries metadata the TCX cannot (name, sport, source, calories, `pictures` references); the TCX carries the uploadable track. By `source`: 94 TRACK_MOBILE, 42 TRACK_SAMSUNG_GEAR, 25 INPUT_MANUAL, 1 IMPORT_GPX. Activities span 2011–2020.
- `resources/gfx/` — the exported photo files: **81 JPEGs** (11.7 MB, largest 310 KB), of which 29 workouts reference **80** via `pictures` entries whose relative URLs resolve here. One file is referenced by no workout — the case the report's "unmatched" section exists for. Verified 2026-07-19: the photos carry **no EXIF segment whatsoever** (JPEG marker walk finds only APP0/JFIF, never APP1), so Endomondo stripped all camera metadata on export; and only **11 of the 80** picture entries carry a `point`.

Out of scope: the export's other folders (`Friends/`, `Profile/`, `Routes/`, `Weights/`, `index.html`) and the loose sibling files in `data/endomondo-strava-exports/` (single-workout exports, a Strava GPX) — none feed the migration.

Strava intake: TCX/GPX/FIT uploads (25 MB cap) or API; API cannot set TCX-borne names/sports (TCX `Sport` is only Running|Biking|Other) and cannot upload photos. The app is a Spring Boot 4.1.0 Thymeleaf web app (built on Spring Framework 7) with the parser as its only service.

Target account (verified 2026-07-19 via the claude.ai Strava connector, athlete id 71292278): the account is **active**, with current runs/walks recorded directly in Strava. Consequences: (a) migrated historical activities (2011–2020) coexist with live data, so any verification or reconciliation listing MUST filter by the historical date range, never "list everything"; (b) the read-only connector is the verification channel for the smoke test and post-run reconciliation (task 7.2/7.3) — it can list and inspect activities but cannot upload, so it does not replace the app's own API client and credentials.

## Goals / Non-Goals

**Goals:**
- One-command (well, one-button) migration of the archive to the user's Strava account: correct routes, dates, titles, sports; no duplicates on re-run; resumable.
- Photo handout report that reduces manual photo attachment to open-link-and-add.
- Every Strava write gated behind explicit user action; dry-run as the default path.

**Non-Goals:** photo upload (API cannot), general Strava client, undo automation, weight/social data.

## Decisions

- **Web-app-hosted OAuth (authorization code)** — the app already serves HTTP, so it hosts `/strava/callback`; the user creates a personal API application on strava.com and supplies client id/secret (`STRAVA_CLIENT_ID`/`STRAVA_CLIENT_SECRET`); refresh token persists in `data/strava-tokens.json` (git-ignored with the rest of personal data). Alternatives rejected: out-of-band token paste (worse UX, same trust model); *committing* a properties file (secrets in git — not what the option below does).
  - **Credential supply: git-ignored `application-local.properties`, not env-var-only, added 2026-07-21** — re-exporting `STRAVA_CLIENT_ID`/`SECRET` in every new terminal session was real, reported friction on Windows. `spring.config.import=optional:file:./application-local.properties` in the checked-in `application.properties` merges an optional local file straight into the same Spring `Environment` that `@Value("${STRAVA_CLIENT_ID:}")` already reads from — env var, system property, or this file, `StravaClient`'s constructor doesn't change either way. A checked-in `application-local.properties.example` template is the copy-paste starting point; the real file is git-ignored, so this is not the "properties file (secrets in git)" alternative rejected above — that was about committing the secret itself, not about a properties file as a mechanism. Rejected: a new `StravaCredentialsStore` mirroring `StravaTokenStore`'s `data/`-JSON pattern — tempting for consistency, but client id/secret are static config set once, not a live, refreshing credential; a store abstraction (with load/save lifecycle) is the wrong shape for something that never changes after setup, and would also conflate `client_id` (not actually secret — Strava puts it in the visible authorize URL) with `client_secret` in the same file as `StravaTokenStore`'s genuinely sensitive tokens.
- **Tracked → TCX upload; manual → manual activity** — tracked TCX carries the route and any sensor data; manual TCX trackpoints are synthetic (observed: a "walk" ending 4:37 AM next day) and would draw false routes, so INPUT_MANUAL workouts are created from JSON metadata only. IMPORT_GPX (1 workout) goes the TCX route.
- **Idempotency: deterministic `external_id` + local ledger** — `external_id` = workout base filename for uploads; Strava's own duplicate rejection is treated as success (existing activity id recorded). Manual creates have no external_id, so the ledger is their only guard: entries are written as `pending` before the API call and finalized after, so a crash leaves a visible reconciliation point instead of a silent duplicate.
- **Sport mapping is a total, reviewed table** — enumerate every distinct sport value in the archive at apply time and map each to a Strava sport type; unmapped values skip that workout with a reason rather than guessing. The dry-run surfaces the whole table for user review before anything uploads.
- **Spring Framework `RestClient` + `MockRestServiceServer`** — no new HTTP or test dependencies: both classes ship with the Spring Framework 7 / `spring-test` artifacts that Spring Boot 4.1 already manages, and Spring Boot auto-configures a `RestClient.Builder` bean. Spring Framework 7 supports binding `MockRestServiceServer` to `RestClient` builders (older versions only bound comfortably to `RestTemplate`). Direction note: the app *consumes* Strava's REST API as an HTTP client; it exposes no REST endpoints of its own.
- **Migration runs in a background thread with a polling status page** — simplest progress UX in the existing Thymeleaf style (auto-refresh); no SSE/websocket machinery for a one-shot personal tool.
- **Report as a single HTML file in `data/`** — sits beside the archive so relative image paths work offline; git-ignored because photos are personal. Generated in dry-run (links "pending migration") and regenerated after runs with live activity links.
- **Photo location: EXIF → picture `point` → workout's first track point** — photos are the one payload the Strava API refuses, so they are handed to the user as geotagged copies instead. Checking the file's own EXIF first is what makes regeneration idempotent (a copy stamped by an earlier run is read back, not re-derived), even though on this archive that source never fires: the exported JPEGs have no EXIF at all, so in practice 11 photos are stamped from their `point` and the remaining 69 from their workout's first track point. Coordinates are written to **copies** under `data/` — the archive is treated as read-only, since it is the irreplaceable original. Alternative rejected: writing EXIF in place (destroys the only copy of the export if the write is wrong).
- **Apache Commons Imaging for EXIF writing** — the archive photos have no APP1 segment, so the library must *create* an EXIF structure, not edit one. Commons Imaging writes EXIF/GPS on JPEGs without native dependencies. Alternative rejected: metadata-extractor (reads metadata but cannot write it).
- **Description stamp** — every migrated activity's description gets "Migrated from Endomondo (recorded {original date})", making migrated items identifiable and manual cleanup feasible. **Credit line added 2026-07-21** (user request): a second paragraph, "Migrated by Piotr Kiraga using endomondo-export-parser: {GitHub URL}", appended after the date stamp and any place sentence — `WorkoutDescription.build()`'s last step, so it lands on every migrated activity unconditionally.
- **Unnamed workouts get a generated "{time of day} {sport}" name** — surveyed 2026-07-20: 104 of 162 workouts (64%) carry no JSON `name`, concentrated in CYCLING_SPORT (70/107) and RUNNING (25/26), so this is an archive-wide gap, not an edge case. Falls back to the same convention Strava itself uses for nameless uploads (e.g. "Morning Run", "Evening Ride"), derived from `start_time`'s local hour and the mapped Strava sport type: Morning 05:00–11:59, Afternoon 12:00–16:59, Evening 17:00–20:59, Night 21:00–04:59. Alternative rejected: leaving the name blank (Strava requires a non-empty name on create) or using the filename timestamp verbatim (unreadable, and duplicates information already in the activity's date field).
- **Location enrichment via OpenStreetMap (Nominatim + Overpass), not a paid API** — decided 2026-07-20, with the user's explicit sign-off on sending workout start coordinates to a public third-party service. Nominatim (`nominatim.openstreetmap.org/reverse`) resolves a coordinate to city/suburb/country; Overpass (`overpass-api.de/api/interpreter`) is queried separately for named features within ~300m (rivers/water, parks, historic sites/landmarks, named boulevards/avenues), because Nominatim's reverse endpoint alone does not reliably surface nearby POIs, only the enclosing address. Alternatives rejected: a paid provider (Google Places/Geoapify) — contradicts the project's credential-free, no-billing posture; a self-hosted OSM extract — far too heavy for a personal tool.
  - **Only the single best-ranked nearby feature is used**, not a full list: priority is water (river/canal/lake) > historic/landmark > park > named boulevard, ties broken by distance. This is a deliberate simplification of "close along the river, starting from the castle" (two features, phrased as a route) down to one feature in one phrase — picking a robust "best of several nearby candidates" heuristic for a *route* is materially harder than for a point, and the single-feature version already delivers most of the value.
  - **Enrichment only ever appends to the generated fallback name, never to a JSON-supplied name** — a human already titled those; appending a location would just make "Regular riding to Kolna - Punctured tire :/" read as "... along Vistula River in Kraków", which is redundant/ugly rather than helpful.
  - **Disk-backed cache keyed by coordinate rounded to 3 decimal places (~110m)** at `data/location-cache.json` (git-ignored) — most of the archive's 162 workouts start from a handful of real-world places (home, work, a few regular routes), so caching collapses what would be ~160+160 lookups down to a handful of real network calls, on this run and every rerun after. This is also what keeps the feature a good citizen of both free services' usage policies.
  - **Self-throttled to 1 request/second per service**, with a descriptive `User-Agent` identifying the app and its GitHub URL, per Nominatim's usage policy. A lookup failure (network error, no result) degrades to the plain "{time of day} {sport}" name / the bare migration-note description — it never blocks or fails the workout it's attached to.
  - **Applies in three places**: the generated workout name (photo report and, later, the Strava client), the migrated activity's description (a sentence appended to the existing "Migrated from Endomondo" stamp), and each photo's caption in the report (replacing the raw `LocationSource` enum name with the resolved place, when available).
- **Strava API client built from the official OpenAPI spec, not the (JS-rendered, unscrapeable) docs pages** — `developers.strava.com/swagger/swagger.json` plus its referenced `upload.json`/`activity.json`/`fault.json` schemas were fetched and read directly (2026-07-20), confirming: `sport_type` is required on activity create and `type` is deprecated (ignored when both present); `POST /oauth/token`'s params are documented `in: query`; `trainer`/`commute` are integers on `POST /activities` (create) but booleans on `PUT /activities/{id}` (update, `UpdatableActivity`) — a real asymmetry, not a typo, so the client does not share one DTO between create and update. No `Retry-After` header is documented anywhere; the 15-minute rate-limit window is documented to reset at `:00/:15/:30/:45` UTC, so a 429 backs off until that boundary and retries exactly once — a second 429 propagates rather than looping, since resuming from the ledger (4.2/4.3) is the intended recovery path for real exhaustion.
  - **Two things Strava does not document anywhere, official or otherwise**: the exact `status`/`error` string contents on an upload, and whether a duplicate-upload rejection populates `activity_id`. Rather than pattern-match strings that could change without notice, `StravaUploadResult.hasActivityId()` alone decides success — if a duplicate rejection does carry an id (community-observed, not contractual), it is treated as success automatically, matching the existing "duplicate rejection counts as success" decision without depending on unstable text.
- **OAuth: `activity:write` scope only, CSRF-guarded via a `state` round-tripped in a short-lived cookie** — the app never reads the athlete's existing activities, so no `read`/`activity:read_all` scope is requested (least privilege). `/strava/connect` generates a random `state` and sets it as an HttpOnly, 10-minute, `/strava`-scoped cookie (not `Secure`, since the redirect URI is plain `http://localhost`); `/strava/callback` rejects any callback whose `state` doesn't match the cookie (and always clears it, so a replayed callback fails even with the right code).
  - **Originally session-stored, switched to a cookie 2026-07-20** — a real end-to-end test produced a spurious "state mismatch": `spring-boot-devtools` is a runtime dependency, and its auto-restart recreates the embedded servlet container (and with it, the in-memory HttpSession store) on any classpath change. A restart triggered by something unrelated (e.g. a background `mvn` build touching `target/classes`) while the browser was away on Strava's authorize page silently wiped the stored `state`, and the callback landed against a fresh, empty session — read by the user as "hangs for quite long time" (the restart) followed by a failure that looked like a real bug. A cookie set on the browser has no dependency on the server process's lifetime, which is the right fit for a single-user local app regardless of DevTools.
  - **The connect button lives on the photo-report page for now**, not a dedicated migration page — 6.1 (which owns "connect status" properly) isn't built yet, and photo-report was already the closest thing to a migration status page in the UI. Expect this to move into 6.1 once it exists, rather than growing two separate connection-status displays.
- **App-wide login disabled 2026-07-21, at the user's request** — `WebSecurityConfiguration` previously required HTTP Basic auth on every page except a handful (`/home`, `/upload`, `/error`, static assets), backed by an in-memory `UserDetailsService` with two hardcoded placeholder accounts (`user`/`password`, `admin`/`admin`) that were never real security, just scaffolding from early in the project. In practice it surfaced as an unexplained browser auth popup with no clear origin, undermining trust in the rest of the security posture (OAuth CSRF cookie, CSRF tokens) rather than adding to it. `securityFilterChain` now permits every request; the dead `spring.security.user.*` properties (already ignored — the custom `UserDetailsService` bean overrode Boot's autoconfigured one) were removed too. CSRF protection is untouched and still active. Acceptable for now since the app only ever binds to `localhost`; revisit with a real scheme (or leave disabled) if that stops being true — see Backlog.
- **Workout report: fully offline for now, no Strava reads** — decided 2026-07-20 with the user, who explicitly floated live cross-checks (e.g. re-verifying sport-type validity, or flagging workouts that already exist in the account by `external_id`) before agreeing to defer them. `WorkoutReportGenerator` reuses `MigrationPlanner` for the actual upload/manual/skip decision (single source of truth — the report never re-implements those rules) and a second scan+parse pass, mirroring how `PhotoReportGenerator` already does its own pass independently of the planner, to resolve each workout's real `WorkoutNaming`/`WorkoutDescription` output (the exact name/description Strava would receive) via `PlaceLookup`. Zero Strava API calls, matching 4.4's structural dry-run guarantee. Same phased pattern as the photo report's `activityIdsByBasename` hook: "already migrated" status can be added once the ledger (4.2) exists, without changing this decision.

## Risks / Trade-offs

- [Strava API surface may have shifted post-cutoff] → consult developers.strava.com at apply time before coding the client; the mocked tests encode our assumptions and the 1–2 activity smoke validates them against reality.
- [Upload processing is async and can fail late] → poll each upload to terminal status; late failures land in the ledger as failed-with-reason and in the run summary.
- [429s / daily cap on a 162-activity run] → throttle ~1 req/s with header-driven backoff; the ledger makes an interrupted run resumable next day.
- [Ledger corruption or manual edits] → ledger is human-readable JSON; reconciliation rule: Strava's duplicate rejection by external_id backstops tracked workouts; manual workouts are few (25) and visually checkable.
- [Real-account writes are irreversible in bulk] → smoke task (1–2 activities) and the full run are explicitly user-gated tasks; dry-run is the default entry point everywhere in the UI.

## Migration Plan

Ships dark: nothing runs until the user opens the migration page. Rollback of the code = revert; rollback of migrated activities = manual deletion aided by the description stamp.

## Backlog (not blocking, revisit later)

- **`data/` layout needs a pass.** It now mixes the read-only input archive (`endomondo-strava-exports/`) with generated outputs and caches (`photo-report/`, `location-cache.json`) at the same flat level, and will grow further with `strava-tokens.json` (3.1) and `strava-migration-ledger.json` (4.2). Worth a deliberate structure (e.g. separating input from generated/cached output, maybe a short `data/README.md` explaining what's what) once the shape of everything that lives there is known — i.e. after 3.1/4.2 land, not before.
- **Placeholder favicon wants replacing.** `static/favicon.ico` is a quick programmatically-generated blue circle with a white "E" (added just to stop 404 log noise) — swap it for something more deliberate later.
- **Workout report could later cross-check live Strava data.** Deferred at the user's request when the report was proposed (2026-07-20): re-verifying sport-type validity against the live API instead of the already-verified static mapping, and/or flagging workouts that already exist in the account by `external_id`. Natural timing is once the ledger (4.2) exists, since "already migrated" is exactly what the ledger tracks.
- **App-wide login was disabled, not designed properly.** Removed 2026-07-21 rather than fixed, since the prior scheme was placeholder scaffolding, not a real design. If this app ever needs to bind beyond `localhost` (a remote host, a shared machine), it needs an actual auth story first — this backlog item is the reminder that "no login" was a deliberate, revisitable choice, not an oversight.
