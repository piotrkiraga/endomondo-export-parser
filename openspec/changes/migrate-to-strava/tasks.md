## 3. Strava client and OAuth

- [x] 3.1 Strava API client on `RestClient`: token refresh, TCX upload + status polling, manual activity create, activity update; env-var credentials; tokens persisted to `data/strava-tokens.json` (verify: unit tests against `MockRestServiceServer` for each call incl. 429 backoff and duplicate-rejection handling). Naming falls back to "{time of day} {sport}" when the JSON `name` is blank — decided 2026-07-20, see design.md; 64% of the archive (104/162) needs this. — Endpoint/field names verified 2026-07-20 against Strava's official OpenAPI spec (developers.strava.com/swagger/swagger.json), not folklore: `sport_type` required on create, `type` deprecated; `trainer`/`commute` are integers on create but booleans on update (asymmetry noted in code); no `Retry-After` header is documented, so the 429 backoff waits until the next :00/:15/:30/:45 UTC boundary instead. Two things Strava does **not** document anywhere — the exact upload `status`/`error` strings, and whether `activity_id` is populated on a duplicate-upload rejection — are handled defensively rather than pattern-matched: `StravaUploadResult.hasActivityId()` is the only success signal used, so a duplicate rejection (if it does carry an id, per community reports) counts as success without depending on unstable string contents. **Still unverified against the real API** — that first real contact is task 7.2's user-gated smoke test, by design. — **Credential supply extended 2026-07-21**: env vars alone meant re-exporting `STRAVA_CLIENT_ID`/`SECRET` in every new terminal session; a git-ignored `application-local.properties` (copied from a checked-in `.example` template, loaded via `spring.config.import`) now works too, with zero changes to `StravaClient`'s constructor since both land in the same Spring `Environment` — see design.md.
- [x] 3.2 OAuth authorization-code flow: connect button → strava.com authorize → `/strava/callback` exchanges the code and stores tokens (verify: mocked-exchange test; manual browser check deferred to smoke) — `/strava/connect` builds the authorize URL (scope `activity:write`) with a random `state` value round-tripped in a short-lived cookie, verified on `/strava/callback` and consumed after one attempt; both endpoints originally stayed behind the app's own login like everything else, until login was disabled app-wide 2026-07-21 (see design.md). A connect/connected status badge was added to the photo-report page since no dedicated migration page (6.1) exists yet. Verified live with a placeholder `STRAVA_CLIENT_ID` (not real credentials): the redirect URL is well-formed, and both the "not connected" and "connected" states render — the latter caught a real bug (an HTML `<template>` tag was used as a Thymeleaf grouping wrapper; its contents are inert in real browsers per the HTML spec, so the whole connect section was invisible despite looking correct in raw curl output — fixed with `th:block`, Thymeleaf's actual non-rendering wrapper). A subsequent test with real credentials surfaced a second real bug: `state` was originally stored in the HTTP session, which a `spring-boot-devtools` auto-restart (triggered by an unrelated classpath change mid-flow) silently wiped, producing a "state mismatch" on an otherwise-correct callback — fixed by moving `state` into an HttpOnly cookie instead, which has no dependency on server process lifetime (see design.md).

## 4. Migration engine

- [x] 4.1 Archive scanner pairing JSON+TCX from a configured directory; migration planner producing per-workout actions (upload / manual-create / skip-with-reason) (verify: unit tests over fixture-built archives)
- [x] 4.2 Ledger (`data/strava-migration-ledger.json`): pending→done/failed lifecycle, resume filtering, duplicate-rejection reconciliation (verify: unit tests incl. crash-between-states case) — `MigrationLedger` persists a `Map<basename, LedgerEntry>` as a basename-sorted JSON array (human-readable/greppable per design.md's reconciliation-risk note), following `StravaTokenStore`'s lock-and-reload-per-call pattern rather than an in-memory cache, since a resumed process must see what an earlier crashed one wrote. Only `DONE` counts as already handled (`isDone`); `PENDING` (crash-interrupted) and `FAILED` are both retried on the next run — a retried upload is backstopped by Strava's own `external_id` duplicate detection (`markDone` records whatever activity id it's given, fresh or from a dup rejection, indistinguishably), matching the accepted risk for manual creates noted in design.md. `markDone`/`markFailed` throw if called without a prior `markPending`, enforcing the pending-before-call sequencing the whole reconciliation guarantee depends on. Exposes `activityIdsByBasename()` (DONE entries only) as the hook the executor (4.3) will pass into `PhotoReportGenerator`, per 5.1's existing note that it takes a plain `Map<basename, activityId>` for exactly this reason.
