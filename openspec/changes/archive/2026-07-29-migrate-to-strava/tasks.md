## 4. Migration engine

- [x] 4.1 Archive scanner pairing JSON+TCX from a configured directory; migration planner producing per-workout actions (upload / manual-create / skip-with-reason) (verify: unit tests over fixture-built archives)
- [x] 4.2 Ledger (`data/generated/strava-migration-ledger.json`): pending→done/failed lifecycle, resume filtering, duplicate-rejection reconciliation (verify: unit tests incl. crash-between-states case) — `MigrationLedger` persists a `Map<basename, LedgerEntry>` as a basename-sorted JSON array (human-readable/greppable per design.md's reconciliation-risk note), following `StravaTokenStore`'s lock-and-reload-per-call pattern rather than an in-memory cache, since a resumed process must see what an earlier crashed one wrote. Only `DONE` counts as already handled (`isDone`); `PENDING` (crash-interrupted) and `FAILED` are both retried on the next run — a retried upload is backstopped by Strava's own `external_id` duplicate detection (`markDone` records whatever activity id it's given, fresh or from a dup rejection, indistinguishably), matching the accepted risk for manual creates noted in design.md. `markDone`/`markFailed` throw if called without a prior `markPending`, enforcing the pending-before-call sequencing the whole reconciliation guarantee depends on. Exposes `activityIdsByBasename()` (DONE entries only) as the hook the executor (4.3) will pass into `PhotoReportGenerator`, per 5.1's existing note that it takes a plain `Map<basename, activityId>` for exactly this reason.
- [x] 4.3 Executor: throttled sequential run over the plan, metadata update after each create/upload, run summary (verify: unit tests with mocked client; re-run test proves no duplicate calls) — `MigrationExecutor` reuses the planner and a new `WorkoutResolver` (extracted from `WorkoutReportGenerator`, which had the identical name/description resolution logic — now both share one implementation so the preview and the real thing can never diverge on what a workout is called). Every created/uploaded activity gets one trailing `updateActivity` call regardless of path: the TCX upload endpoint has no `sport_type` parameter at all (TCX's own `Sport` element is limited to Running\|Biking\|Other), so only that trailing call can set the archive's precise mapped sport type. That call is best-effort — the ledger marks `DONE` as soon as an activity id exists (before the update), since the id is what prevents a duplicate on a re-run, not whether the cosmetic correction succeeded; a failed correction lands in the run summary's separate `metadataWarnings` rather than `failures`, since nothing actually failed to migrate. Throttled via the same `RequestThrottleUtil` the OpenStreetMap clients use (~1 req/s, design.md's mitigation for 429s/daily caps). 9 new unit tests against `MockRestServiceServer` incl. a still-processing poll loop, a duplicate-rejection-still-counts-as-success case, an already-DONE resume test making zero HTTP calls, and an explicit re-run test proving a second pass over the same ledger makes no further calls. Wired into a controller/page by 6.1 (`MigrationReviewController`), which calls `migrateOne` directly rather than this bulk `run`. — **Extended 2026-07-21 with old-bike gear correction** (design.md), once the user created the old bike as Strava gear and supplied its id: the same trailing `updateActivity` call now optionally sends `gear_id` for a Ride on or before a configured cutoff date (`MigrationExecutor.gearIdFor`), both values read from `application-local.properties` as personal account data, blank/unset by default. 6 new tests (2 on `StravaClient` proving `gear_id` is included only when given and never sent as JSON `null`; 4 on `MigrationExecutor` covering before/after the cutoff, unconfigured, and non-Ride sports).
- [x] 4.4 Dry-run path shares the planner and performs zero API calls (verify: unit test asserts no interaction with the client) — enforced structurally: `MigrationPlanner` has no Strava collaborator to call, so a plan cannot reach the network

## 6. Web UI

- [x] 6.1 Migration page — one workout at a time, interactive review; redesigned with the user 2026-07-21 from the originally planned bulk execute-button page (full rationale in design.md) (verify: unit tests over the controller's routing/model logic incl. redirect chains and resume-vs-forced-remigrate; live GET verification against the real 162-workout archive)
  - **Routing** — `MigrationReviewController` at `/migration/review`, addressing workouts by position in the plan's actionable order. Recomputed per request, never held in session state, so a bookmarked URL always means the same workout and the page survives a restart.
  - **Per-workout screen** — exact resolved name/sport/description/dates via `WorkoutResolver` (the same one 5.1 and 4.3 use), plus a photos section: each geotagged copy shown as an actual thumbnail (served via the existing `/photo-report/**` resource mapping — the review page reuses `endomondo.photo-report.output-directory`, not a directory of its own) next to its absolute local path in a `readonly` input, click-to-select, for pasting into Strava's own attach dialog.
  - **Buttons**:
    - **Migrate** — calls `MigrationExecutor.migrateOne` directly; always available, including as a re-migrate override once already `DONE`/`SKIPPED` — never `run`'s bulk pass.
    - **Skip** — only before a decision exists; `MigrationLedger.markSkipped`, a new durable status; no Strava call.
    - **Previous** / **Next** — plain `<a>` links, not POST forms (neither mutates anything, so neither should be a form): **Previous** always available except on the first workout; **Next** only once a decision exists for the current one, so the migrated/failed flag and photo paths stay on screen until you're done with them.
    - **Stop** — always available; jumps to a summary screen tallying uploaded/manual/skipped/failed/remaining across the whole plan by reading the ledger, not by re-calling Strava.
  - **Testing** — no `MockMvc`/Thymeleaf test harness: a full `@SpringBootTest` would wire the real, already-connected `StravaClient` into any accidental `/migrate` POST. Controller tests instead call the controller's methods directly against a `MigrationTestSupport`-built rig (mocked HTTP, temp-dir ledger/tokens) — 15 tests, plus 2 more for the `hasPrevious`/`hasNext` model flags once `next` stopped being a controller endpoint. Actual template rendering (record property binding via Thymeleaf's SpEL, redirect chains, real photo paths, thumbnails) verified live via GET-only browser screenshots against the real archive, deliberately never clicking Migrate to avoid a real, ungated Strava write.
  - **Follow-up from the user's first real click-through (2026-07-21)**: photo thumbnails and a Previous button were both missing from the initial build — added the same day (`MigrationReviewController.PhotoPreview` pairs each copy's servable URL with its local path; `hasPrevious`/`index - 1` mirror `hasNext`/`index + 1`). Also surfaced a real Strava behavior — old-bike gear correction, implemented same day; see task 4.3 and design.md.
  - **Second follow-up, same day, from continued real use**:
    - `MigrationExecutor.migrateOne` on an already-`DONE` workout used to force a full re-upload — which Strava's own duplicate detection then rejected as a failure (visible on the very first real Ride migrated). Re-clicking Migrate on a `DONE` workout now skips straight to the trailing metadata-update call against the existing activity id instead, so a re-click safely refreshes name/sport/description/gear without ever re-sending the track.
    - `start()`'s "jump to the first undecided workout" only excluded `DONE`/`SKIPPED`, not `FAILED` — so a workout that failed once got re-selected as "the next thing to review" on every fresh visit to `/migration/review`, which read as an automatic retry even though no HTTP call was actually being made. `FAILED` now counts as decided there too, matching `hasDecision` everywhere else on the page.
    - **Next** was gated behind `hasDecision`, forcing a decision before you could even look ahead; changed to `hasNext` (position-based) so Previous/Next browse the whole plan freely, independent of what's been decided — Migrate/Skip remain the only way to actually act.
    - Previous/Next/Skip used to appear and disappear from the button row depending on state (`th:if`/`th:unless`), which visibly reflowed the row between workouts; all three are now always rendered, grayed out (Bootstrap's disabled-link/disabled-button pattern) when not applicable, instead of toggling in and out.
    - That same row had a real CSS bug once the buttons stopped toggling: the bare `<a class="btn">` elements blockify differently from `<form><button>` under Bootstrap's default flex `align-items: stretch`, and `<form>`'s own default `margin-bottom: 1rem` inflated the row's cross-size further — together producing a ~16px vertical offset between link-styled and form-styled buttons. Fixed with `align-items-center` on the row plus `mb-0` on each form.
    - Strava's own duplicate-upload error message is an HTML fragment (a real `<a>` to the pre-existing activity) coming back through the upload-status endpoint; the review page's `th:text` was escaping it to literal `<a href=...>` text instead of a clickable link — switched to `th:utext` for the failure-reason spans on both the per-workout card and the summary page, since that text is always either a fixed string or Strava's own trusted response, never archive/user-controlled content.
    - The "archive: {basename}" line was replaced with a localized "Source: {relative file path(s)}" line (`ResolvedWorkout.sourceFiles()`), after the user asked what the old marker was even for and then asked for it to show the real file(s) on disk instead of a bare filename stem — see design.md.
    - The workout details table (Sport/Start time/Distance/Duration) was restyled from a bordered Bootstrap `<table>` into a shared `.detail-list`/`.detail-row` label-value component (`static/css/app.css`), applied identically to the Upload view's "Workout summary" table (a base-parser page, outside this change's own scope, but sharing the one stylesheet so the two look identical rather than each keeping its own bordered table) per the user's explicit ask to make the two consistent.
