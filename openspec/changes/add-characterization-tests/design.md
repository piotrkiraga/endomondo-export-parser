## Context

`UploadController.processEndomondoJson` (private, ~160 lines of hand-rolled map-walking) is the only parsing logic. Code reading predicts several defects the tests must pin:

- **Type-cast crashes**: entries are cast blindly (`(Integer)`, `(Double)`). Real files carry decimal `calories_kcal` (e.g. 491.268 → `Integer` cast) and integer `altitude_min_m`/`ascend_m` (→ `Double` cast), so parsing real exports should throw `ClassCastException` at the first mismatched entry. Fields before that entry (file order) are populated.
- **Points lost**: `setPoints(points)` sits after the per-key `if/continue` chain, so it only runs for unrecognized keys; every recognized-key entry skips it. `EndomondoJson.points` defaults to an empty list, so the result shows empty (not null) points.
- **Point fields unreachable**: each point is a list of single-key maps but only `.get(0)` (the `location` map) is examined, so altitude/distance/speed/timestamp branches never fire — and those branches read from the wrong map (`endomondoJsonProperties`) anyway. Same `.get(0)` pattern loses `longitude` inside `location`. Unobservable through the returned object while points are lost — recorded here, not in the spec.
- **Error handling**: only `JsonParseException` is caught by the upload flow; a `MismatchedInputException` (valid JSON, wrong shape) or `ClassCastException` escapes to the global error handler.

The project does not compile on the machine's JDK 17 (Lombok 1.18.12).

## Goals / Non-Goals

**Goals:**
- Compilable project on JDK 17 with the smallest possible dependency change.
- Characterization tests that run with `mvnw test` and pin observed parser behavior on the committed fixtures.
- Spec deltas that match *observed* behavior — if a test contradicts the predicted spec scenario, the spec delta is corrected to what was observed before archiving.

**Non-Goals:**
- Fixing any pinned defect; upgrading anything besides Lombok; testing the web layer or TCX files.

## Decisions

- **Lombok 1.18.30, nothing else** — first Lombok line with stable JDK 17+21 support that predates the Boot 3 migration. Alternative (delomboking or downgrading the JDK) rejected: larger footprint, throwaway work.
- **Test seam: widen `processEndomondoJson` to package-private** — smallest possible seam; `UploadController` is instantiated directly in the test (the method touches only the static logger and Jackson, no Spring context needed). Alternatives rejected: reflection (brittle, obscures intent), extracting a parser service now (a real refactor that deserves the safety net it would be creating).
- **Plain JUnit 5, no `@SpringBootTest`** — no context boot keeps the suite instant and proves the parser has no container dependency. `MockMultipartFile` from spring-test supplies the `MultipartFile` argument.
- **Observation-first workflow** — write each test by running the parser and recording the outcome, not by asserting the prediction above. Predictions guide *what* to probe, observations decide *what* to assert.

## Risks / Trade-offs

- [Lombok bump changes generated bytecode subtly] → same annotations in use (`@Getter/@Setter/@ToString`); generated members are API-identical, and compile success + green tests is the check.
- [Package-private seam invites production code to call the parser directly] → acceptable short-lived risk; the parser-fix change extracts a proper service.
- [Tests encode defects and later read as intended behavior] → every defect-pinning test carries a comment naming it a characterization of a known defect, mirrored by "(pinned defect)" requirements in the spec.

## Migration Plan

Additive only (one version property, one visibility keyword, new test files). Rollback = revert the commit.
